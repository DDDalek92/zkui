# D01-C：数据库初始化失败即停止

2026-10-15；基线 `551fcf076595cd04c32e44a7011b932ca3c5b85d`（Fork #22）。
此增量不升级 H2/Flyway、不迁移用户库，不改 V1 或删除版本记录。

## 实际复现与行为

新增 `DatabaseStartupIT`，用测试临时目录、随机合成数据库口令和真实组装 JAR：

- 修改前，错误口令、未纳管的非空 schema、已应用 V1 但缺失 histories 三项均失败：子进程继续运行，而非因初始化失败退出。正常新建/重启用例通过（4 项中 3 失败、0 错误）。
- 修改后，`Dao.checkNCreate()` 的迁移异常向上传播为固定、无 JDBC 原始 cause 的错误；`Main` 在构造和绑定 Jetty 前调用它，子进程非零退出。
- Flyway 成功后执行零行 SELECT，核对真实 histories 表和读取所需列；不把“元数据已应用”误当表仍可用。不加载历史行或试写审计数据。
- 三项负向回归要求有固定错误、无合成口令回显、无 connector 启动日志、进程结束后端口可绑定；错误口令后原历史可读，未知 schema 的 marker 不变，缺表后原 V1 成功记录仍保留。
- 正向回归分别以真实 JAR 新建库、重启已有库；独立 JDBC/DAO 重新读取确认一条合成历史保留。不是用登录 200 替代数据库保存断言。

## 运维变化及限制

数据库认证、迁移或必需表读取失败，现在是启动失败，不再提供一个“登录正常但数据库损坏”的实例。排障应在隔离副本中核对驱动、权限、数据库结构及 Flyway 元数据；不要用 dev/clean、baseline/repair 或删除记录来绕过门禁。

门禁只验证迁移和最小读取能力，不证明写权限、磁盘空间、所有约束/索引或启动后的数据库可用性。`insertHistory()` 的既有 best-effort 策略仍保留，写失败不等于持久化成功；严格审计写入策略仍需独立设计。显式 env=dev 的历史清库行为没有改变，不能用于用户库。

H2 仍为 1.3.174、Flyway 仍为 2.2.1；#22 的 2.5.252 驱动仅限隔离测试。完整跨版本应用/Flyway迁移、失败中断/锁/不可写矩阵、约束及差量恢复仍未放行；I02、MySQL 与依赖审计继续保留。

本地 OpenJDK17 完整 `clean verify`：16 单元 + 88 集成 = 104 项，0 失败/错误/跳过，含本增量4项真实JAR回归及3项隔离H2预演。本机未执行Chrome或Docker。
