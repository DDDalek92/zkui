## 阶段 M3：整合社区 PR

1. 低风险：#87、#109 等能独立验证的小改动。

每项必须注明上游作者、原 PR 链接、处理理由、新 Fork PR 和验证结果。

## 阶段 M5：发布维护版并开启二次开发

发布候选例如 `v2.0.0-maintenance.1`（名称仅建议），需要：
- [ ] 关键 CRUD、搜索、导入导出、LDAP/ACL 安全边界均通过测试。
- [ ] 已知 P0 漏洞处理完毕，P1 有清晰追踪与发布说明。
- [ ] JDK / Docker 部署可复现、依赖清单及兼容说明齐备。
- [ ] 历史库迁移、数据备份与恢复演练有记录。
- [ ] 原 Issue/PR 处理台账齐全，主要变更可追溯。
- [ ] 用户审核后发布，不使用自动批量合并。

## 推荐首十项任务

1. 真实构建并记录失败（M0）。
2. 在隔离环境运行 ZooKeeper + zkui 基线冒烟（M0）。
3. 增加 JUnit 与 ZK 集成测试骨架（M1）。
4. 部署基线 CI，避免无测试合并（M1）。
5. 验证/修复 USER 对 `/import` 的潜在越权（M2）。
6. 验证/修复匿名 REST 泄漏与默认配置（M2）。
7. 验证会话轮换、CSRF 与上传/URL 安全（M2）。
8. 整合 #87 与 #109（M3）。
9. 验证客户端 ACL/Digest 及 LDAP，再处理 #50/#107（M3）。
10. 在历史数据副本上规划 H2/Jetty/驱动升级（M4）。

## 工作协议

每项用 `maintenance/<topic>` 或 `fix/<topic>` 分支单独提交 → CI → 审阅 → 合并到受保护的 `master`。绝不直接批量关闭原作者仓库 Issue；对作者贡献保留来源。动态测试未完成的结论标记“待验证”。
